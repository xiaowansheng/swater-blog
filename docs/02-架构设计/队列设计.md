# 队列设计文档

## 1. 队列概述

Swater Blog 后端采用基于 SPI（Service Provider Interface）插件机制的消息队列设计。当配置启用 `plugin.mq.active=rabbitmq` 时，系统底层切换为 RabbitMQ 提供异步消息投递能力；若未配置或为 `memory`，则自动降级为应用内内存队列以保障系统在无外部组件时的正常运行。

## 2. 队列设计与配置

系统中主要定义并注册了两个核心队列：

| 队列名 (Queue) | 对应常量 | 说明 | 持久化 | 消费者 (Consumer) |
|---|---|---|---|---|
| `notification.queue` | `QueueConstant.NOTIFICATION_QUEUE` | 统一通知队列（含评论、登录、系统等所有类型的通知） | 是 | `RabbitMqNotificationConsumer` |
| `message.verification.queue` | `QueueConstant.VERIFICATION_CODE_QUEUE` | 验证码/短信验证消息队列 | 是 | `RabbitMqVerificationCodeConsumer` |

### 2.1 声明机制
在 Spring 中，这两个队列由 `MqQueueConfig` 配置类在激活 RabbitMQ 插件时自动注入声明：
```java
@Configuration
@ConditionalOnProperty(name = "plugin.mq.active", havingValue = "rabbitmq", matchIfMissing = false)
public class MqQueueConfig {
    @Bean
    public Queue notificationQueue() {
        return new Queue(QueueConstant.NOTIFICATION_QUEUE, true);
    }

    @Bean
    public Queue verificationCodeQueue() {
        return new Queue(QueueConstant.VERIFICATION_CODE_QUEUE, true);
    }
}
```

## 3. 消息投递机制

系统通过 `MQService` 屏蔽底层消息队列的实现细节，通过 `MessageQueuePlugin` 的 `sendToQueue` 接口直接将消息路由到对应的队列。投递时使用 RabbitMQ 的默认直连交换机（Default Exchange `""`），以队列名作为 Routing Key。

```text
  [业务层/服务层]
       │
       ▼
   [MQService] (通过 MessageQueuePluginFactory 查找启用插件)
       │
       ├─────────────────────────────────┐
       ▼                                 ▼
[RabbitMQPlugin]                  [MemoryMQPlugin]
       │ (RabbitMQ 投递)                 │ (内存队列异步投递)
       ▼                                 ▼
 `notification.queue`           内存阻塞队列 (BlockingQueue)
```

## 4. 核心消息格式与处理流程

### 4.1 统一通知消息
* **队列名称**：`notification.queue`
* **消息格式** (NotificationMessage)：
```json
{
  "notificationId": 12345,
  "userId": 1,
  "type": "comment",
  "title": "新评论通知",
  "content": "张三 评论了您的文章《Hello World》: 写的不错！",
  "timestamp": "2026-07-06T18:40:00",
  "data": {}
}
```

* **处理流程**：
  1. 业务发生变化（如评论审核通过或用户登录成功），调用 `NotificationServiceImpl.sendNotification()`。
  2. 系统向数据库写入一条处于 `QUEUED` 状态的 `sys_notification` 记录。
  3. `NotificationServiceImpl` 在数据库事务成功提交后（`EventUtil.publishEventAfterCommit`），异步向消息队列投递 `NotificationMessage`。
  4. `RabbitMqNotificationConsumer` 消费消息，并调用 `NotificationServiceImpl.processNotificationMessage()`。
  5. 消费者解析消息，调用启用通道插件（如 WebSocketChannelPlugin 发送实时弹窗、EmailChannelPlugin 发送邮件），并将该通知在数据库的状态更新为 `SENT`。

---

### 4.2 验证码消息
* **队列名称**：`message.verification.queue`
* **消息格式** (VerificationCodeMessage)：
```json
{
  "recipient": "user@example.com",
  "code": "123456",
  "type": "EMAIL",
  "timestamp": "2026-07-06T18:40:00"
}
```

* **处理流程**：
  1. 页面请求发送邮箱或短信验证码，调用 `MessageVerificationServiceImpl.send()`。
  2. 构造并发送消息至 `message.verification.queue`。
  3. `RabbitMqVerificationCodeConsumer` 消费消息，调用邮件服务或短信服务商 API 发送验证码。

## 5. 可靠性设计与重试

1. **事务后置发送**：
   所有的 MQ 消息发送逻辑都包装在 `EventUtil.publishEventAfterCommit` 中，确保数据库记录成功持久化后再向 MQ 发送消息，防范“数据库回滚但消息已发出”导致的业务脏数据。
2. **状态记录与自动重试**：
   通知表 `sys_notification` 记录了通知的发送状态（PENDING/QUEUED/SENT/FAILED）和发送次数。在消息投递失败或处理异常时，后端将状态更新为 `FAILED`，并计算下次重试时间。
   系统通过 Quartz 定时任务调用 `retryFailedNotifications` 对失败记录进行自动出队重试，直至达到 `max_retry_count`（默认3次）。
